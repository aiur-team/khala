# P14 device-loss boundary: implementation and proof still required

This note records the remaining work behind the recovery row of `security-acceptance.md`. It is not acceptance evidence. P14 says that after a participant loses every device, earlier history is irrecoverable: no Khala escrow, connector, transport, or other participant may restore it. A replacement device may participate only after fresh authorized admission and must receive no earlier content. P12's ordinary invitation policy does not authorize silent readmission of a revoked participant.

## What exists

- `packages/messaging/src/browser-device/service.ts` detects mismatched or absent local key material and keeps `lost` sticky. Its `acceptLoss` primitive is not wired into the hosted application. `apps/web/src/composition/human/browser-api.ts` also retains the old Matrix device ID in local storage. Clearing a local flag alone would reuse that ID and cannot be a replacement-device admission.
- The signed-in human application now renders a reachable lost-key screen outside every room route. It directs the user to an existing retained device or profile but grants no room access, replacement identity, or admission. Loss stays sticky in the current application instance, so a same-page retry would not re-examine restored keys. The former recovery panel remains inside the ready room route, so it cannot serve as the entry point after key loss.
- Matrix membership and `history_visibility: joined` attach to the user, not this browser device. The existing invite inspection treats an already-joined user as joined, and the admission gateway does not establish a per-device history cutoff. These paths cannot prove a new device is admitted without backfill. The pinned SDK disables automatic room-key requests in its Rust crypto startup, but that source fact is not a live no-backfill guarantee. Human browser crypto does not currently set the connector's verified-only recipient policy, so future room-key sharing to a newly visible device needs explicit examination.

## Required production boundary

1. Bind a newly created Matrix device ID and its verified key fingerprint to the authenticated provider principal and the exact owner. Persist an admission state for that device separately from the existing user-level room membership. Reject an old, revoked, or mismatched device and every stale account/session response. A replacement must not inherit old participation just because the Matrix user remains joined.
2. Add a protected admission operation whose authority follows the approved G-ADMISSION decision. Decide the required owner/browser confirmation in that decision; this note does not choose it. P12 invitation redemption is usable only where its existing policy actually authorizes this device and does not silently readmit a revoked participant. Maintain a stable operation ID and a server-side event or key epoch cutoff for every affected channel.
3. Fence application-visible reads and sends at the protected API, timeline/feed, and browser UI against the admitted device and cutoff. Matrix history visibility alone is insufficient. Rotate the sender's outbound room session when admitting the replacement; do not forward, export, request, or back up earlier room keys to it. Other current members must also honor the cutoff before sending new content to the replacement. Old transport ciphertext may still exist; possession of those bytes must not yield old plaintext through pagination, direct event reads, listener feeds, or restarts.
4. Only after the protected admission succeeds may the browser create or activate the replacement device's room route. Preserve the retained-profile reopen path and do not turn the lost-key screen into implicit `acceptLoss` or automatic room rejoin.

## Live acceptance to run after the boundary exists

Use the existing secret-free two-OAuth human fixture descriptor and the real protected hosted HTTP service. In a persistent browser profile, create and join a channel through the production UI, send an encrypted message, record its event ID, device ID, and key fingerprint, then close the browser process. Reopen the same profile in a distinct process and prove that the same device decrypts that exact event. The mounted browser regression in this change only checks the ordinary ready screen with a synthetic ready port; it is not this retained-key crypto proof. For total loss, remove every profile holding one participant's keys, sign in as that same provider subject from a fresh profile, and observe a new Matrix device ID. Before fresh admission, protected room routes and application-visible event/feed reads must refuse it. After the approved admission, send a new encrypted event and prove the replacement decrypts it but cannot decrypt the exact older event even if the transport returns its ciphertext; direct application reads, key requests, backup, another participant, pagination, and restarts must not provide the older plaintext or keys. Inspect the owned server and connector state for forbidden escrow or backfill. Exercise a revoked former participant separately so a generic already-joined verdict cannot bypass readmission authority.

The current `tests/e2e/security/security.test.ts` recovery case deliberately skips. Component tests, SDK probes, and the lost-key screen regression do not turn that row green. The hosted service, two real OAuth owners, final admission decision, per-device cutoff and sender-key implementation, and guarded live evidence are prerequisites to remove the skip.
