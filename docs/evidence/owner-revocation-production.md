# Hosted owner revocation evidence (2026-09-26)

Issue #344 composes KHA-128 for an authenticated owner and an exact bound connector device. The control plane journals the operation and disables the binding and adapter capability before reconciling Matrix removal. The connector's isolated Chromium Matrix SDK checks its own published Curve25519 key and attempts `deleteDevice` after stopping delivery. A DPoP-bound cleanup receipt cannot authorize ordinary mailbox, release, or send routes after disable.

The exact room send fence records permits by sender and Matrix transaction ID before either browser or connector SDK sends. An owner revocation seeds its sender set from live joined-member, owner-room-index, and published-device queries, then writes a durable hold before the first protocol call. Existing permits with unknown Matrix outcomes remain pending until the same transaction ID is retried or read back. Each surviving Khala browser or connector sender must call its own SDK `forceDiscardSession(roomId)` and submit an authenticated operation/epoch receipt; rotation remains pending while any sender is offline or unverified. A newly opened sender must discard before its first permit. Existing external Matrix clients are outside the Khala adapter sender guarantee; no server process holds Megolm keys or message plaintext.

On a disposable Synapse 1.161.0/Postgres 16 project with matrix-js-sdk 42.4.0, Playwright 1.63.0, Chromium 150.0.7871.128, and Node 22.23.2, the connector SDK's `forceDiscardSession` succeeded. `deleteDevice` for its own exact device returned HTTP 401 (interactive authentication); the SDK error exposed `httpStatus` without an `errcode`, so the connector maps either signal to `reauthentication_required`. The control Matrix adapter then used its existing derived password for the same agent account on a separate control device. It observed the expected published Curve25519 key, completed the advertised `m.login.password` UIA challenge, and independently queried the device endpoint again. Observed sequence: `discard=true`, endpoint `reauthentication_required`, before `present`, UIA `removed`, after `removed`. The password stayed in the control process; the connector received neither password nor admin credential. The disposable Docker project, volumes, and Chromium profile were removed after the check.

The reproducible runner is [`scripts/acceptance/owner-revocation-live.ts`](../../scripts/acceptance/owner-revocation-live.ts). It ran after the managed sender inventory helper commit `0bb17c65` and UIA helper commit `3d997a4f` were cherry-picked onto the #344 branch. Exact command: `PATH=/home/everdred/.local/share/mise/installs/node/22.23.2/bin:$PATH TMPDIR=/home/everdred/.cache/t344 pnpm exec tsx scripts/acceptance/owner-revocation-live.ts`. The sanitized one-line log is `/home/everdred/.cache/t344/owner-revocation-live.log`; no account secret, Matrix token, or device key appears in it. The runner asserts that a published key exists before deletion and that the independent status changes from `present` to `removed`; it reports only those status values. It creates and removes its own disposable no-JWT Synapse configuration, Docker project, volumes, and browser profile.

This live check proves the selected SDK discard and UIA removal effects with disposable devices. It does not prove a full hosted owner request through all routes, loss/restart recovery, or rotation from several independent online browsers and connectors. Focused store/route tests cover hold/acquire races, unknown and cancelled permits, exact owner/device/generation checks, wrong-sender receipt rejection, durable removal readback, and per-sender rotation. No claim is made that revocation recalls content or keys already received, deletes remote copies, recovers all lost keys, or backfills history. A definite removal refusal leaves the operation partial and, per KHA-128's existing port contract, lifts the temporary hold; it does not establish cryptographic exclusion.
