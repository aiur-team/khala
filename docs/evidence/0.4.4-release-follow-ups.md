# 0.4.4 release follow-up verification

Verified on 2026-10-05 with Node 22.23.2, pnpm 10.34.5 and matrix-js-sdk 42.4.0. No Netlify command or deployment was used.

## Saved-secret rejoin

The published `khala-cli` 0.4.2 and 0.4.4 tarballs were unpacked and run as actual MCP stdio processes with isolated state directories and the same Codex session ID across each restart. A localhost HTTP harness served the control join/poll/ready handlers, using the real control store adapter over in-memory durable blob fixtures. Human authentication/membership adapters supplied the owner; registration, login, invitation and agent room joins used a running local Synapse. Production `825b365d` agent-join modules were loaded from that commit; baseline main was `c4555301` (the workspace's starting head).

For each combination, the first MCP join was human-confirmed, invited and observed `connected`; MCP was stopped and restarted; a second join used the retained session ID and secret. The harness checked both requests carried the same identity fields.

| Packed CLI | Control handlers | After restart |
| --- | --- | --- |
| 0.4.2 | `825b365d` | `awaiting_confirmation` |
| 0.4.4 | `825b365d` | `awaiting_confirmation` |
| 0.4.2 | baseline main `c4555301` | `awaiting_confirmation` |
| 0.4.4 | baseline main `c4555301` | `awaiting_confirmation` |
| 0.4.2 | this change | auto-confirmed, then `connected` |
| 0.4.4 | this change | auto-confirmed, then `connected` |

This is missing hosted control approval reuse, rather than a 0.4.4 client regression. Both old versions already send the saved secret and understand `autoConfirmed`. Older control remains compatible but asks again. Existing sessions first approved on old control need one confirmation on upgraded control to establish the persistent approval record.

The control unit regression uses the real store and both human/agent handlers: approval survives expired join records; a changed secret, session or harness stays pending; owner membership loss and removal prevent automatic provisioning. Initial human confirmation and subsequent automatic confirmation use the same provisioning and removal checks.

## Hosted encrypted history

A separate live Synapse check created an encrypted room with `m.room.history_visibility: shared`. The sender encrypted a message before inviting a fresh agent through the REST invite endpoint, which does not forward historical room keys. The recipient reproduced the SDK's “sent when we were not a member” decryption failure. `history()` returned the unavailable-key placeholder, did not expose the original plaintext, and a message encrypted after joining decrypted live.

Shared visibility permits fetching ciphertext; it does not guarantee keys. The browser's verified-inviter MSC4268 path can share earlier keys, as covered by the existing [Matrix agent acceptance evidence](m1-node-matrix-agent.md). Missing historical keys remain an expected possibility; this change neither forwards keys nor widens history visibility. The existing live scenario for an unsigned inviter now also asserts the placeholder. Unit coverage checks a mixed history page and continued pagination through an entirely undecryptable page.
