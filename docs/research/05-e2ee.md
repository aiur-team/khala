# End-to-end encryption and endpoint boundaries

Research continuation, 16 September 2026. Read [architecture](06-architecture.md) for the current substrate comparison. The user approved connector-enforced gating: pending plaintext may be available to the trusted owner connector; only released content enters model context. This document supersedes the recovered E2EE placeholder; the recovered custody, inference and MLS ecosystem reports remain historical supporting material.

## Current priority: TypeScript, existing crypto and Netlify-compatible delivery

User steering: maximise off-the-shelf open source reuse, use TypeScript, and prefer Netlify Functions/Blobs; a Railway backend is acceptable when it saves implementation work. Existing agent sessions must be attachable across model vendors. Connector-enforced review is approved; Matrix is an option, not a selected substrate. Compare managed Matrix plus Netlify product services against a Netlify ciphertext relay using a vetted OSS crypto engine. Strict cryptographic exclusion of the trusted connector is outside the baseline. A Matrix path should reuse its existing E2EE as designed.

The Matrix JavaScript SDK runs in browsers and Node, uses Rust crypto through WASM, and supports secret storage, cross-signing, backups and verification. Its browser crypto store defaults to IndexedDB. The documented non-browser in-memory mode requires a fresh device on restart; that example is not durable unattended connector storage. Its README warns that multiple clients sharing one crypto database can corrupt state. [Matrix SDK documentation](https://raw.githubusercontent.com/matrix-org/matrix-js-sdk/develop/README.md). Its current license file is Apache-2.0; this is source evidence for this SDK, not a statement about every Matrix server/client component. [SDK license](https://raw.githubusercontent.com/matrix-org/matrix-js-sdk/develop/LICENSE).

Proposed mapping: each human uses their own Matrix account; each agent participant has a separate bot account and explicit device instances, linked to its owner in Khala's approved binding. Do not add the bot as another device on the human account, which would confuse authorship and expand secret-sharing authority. Khala policy remains keyed to human owner, agent account/device, room and sender. A Matrix display name is not that binding.

Matrix feasibility acceptance:

- Four independent participants exchange encrypted events on a pinned homeserver/SDK combination. Agent content remains out of the model context until explicit release; test direct harness reads and logs as well as the happy UI.
- Device verification, unknown-device handling, cross-signing reset and bot replacement are visible and require the intended owner authority. Avoid silently trusting every device for convenience.
- Restart the connector with supported persistent crypto storage and retained device identity; evaluate the TS-accessible native binding described below if browser-style persistence is unsuitable. Document exact SDK/provider APIs rather than adopting an ephemeral demo.
- Reconnect after event receipt and after context insertion: deduplicate by stable Matrix event/release IDs and reconcile acknowledgement uncertainty without presenting storage receipts as model execution.
- Prove room-history settings, room-key requests, encrypted backup restore and newly verified devices follow the chosen disclosure policy. Homeserver history visibility and possession of decryption keys are distinct controls.
- Only if a future stronger boundary is requested, compare separate encrypted Matrix rooms and a unified Khala projection before building MLS. Verify the bot cannot acquire pending-room keys through device verification, key forwarding, backups, attachments or history import.

Room membership, power levels and room state remain Matrix policy surfaces. Sensitive review notes and release bodies belong in encrypted content; do not assume custom state events are encrypted. These proposals reuse the [Matrix client-server encryption and key-management model](https://spec.matrix.org/latest/client-server-api/#end-to-end-encryption); the feasibility work must verify the precise supported behavior.

The connector binds each approved delivery to an existing harness session, independently of crypto device identity. Restarting a connector must not accidentally create a new coding session or redirect queued deliveries. “Any model” means model-agnostic message handling through explicit harness adapters; it does not imply every harness supplies the same attachment or acknowledgement API.

## TypeScript endpoint and hosting comparison

Keep application code in TypeScript. Rust cryptography embedded through WASM or a prebuilt Node binding is a dependency choice; a standalone Rust connector is a separate cost and has not been approved. In every design, decrypted pending messages and active crypto state live on authorised user devices/connectors. A Railway backend, if selected to reduce development effort, has the same ciphertext-only obligation as Netlify. Netlify Functions can authenticate/store/route opaque records; Blobs can retain ciphertext or client-encrypted backups, never the plaintext secret needed to unlock them.

| Candidate | Existing OSS available | Persistence and remaining proof | Hosting implication |
|---|---|---|---|
| Matrix browser or desktop renderer in TS | `matrix-js-sdk` with Rust/WASM crypto | Real persistent IndexedDB; single active client per crypto DB; verify refresh, app restart, quota and key unlock | Netlify hosts UI/product APIs; an external Matrix homeserver still supplies Matrix services |
| Matrix Node connector in TS | `matrix-bot-sdk` plus `@matrix-org/matrix-sdk-crypto-nodejs` | Local file-backed crypto provider exists; prove pinned SDK/native-binding compatibility, owner verification and restart stability | Native dependency runs on user's machine, not an E2EE endpoint inside Netlify |
| Custom TS integration of Node crypto binding | Native `OlmMachine` exposes persistent SQLite | Reuse crypto state machine but implement/adapt Matrix sync, outgoing requests and verification lifecycle | More integration ownership; not a substitute for a homeserver |
| Netlify relay plus TS/WASM MLS endpoints | OpenMLS or mls-rs core | Browser/Node bindings and transactional local storage need feasibility work; no supplied Khala invitation/history/recovery UI | Functions/Blobs remain ciphertext delivery/storage; crypto work is on endpoints |
| Netlify relay plus low-level encryption primitives | WebCrypto or other maintained OSS primitive libraries | Primitive availability does not provide membership, device verification, ratchet recovery or group key lifecycle | Do not assemble a new chat cryptographic protocol to avoid a hosted dependency |

**Actual Matrix JS storage source:** `MatrixClient.initRustCrypto` selects a store prefix or `null`; the Rust crypto initializer opens `StoreHandle`, whose WASM implementation chooses IndexedDB when named and memory otherwise. The ordinary `cryptoStore` option is passed as a legacy store for migration. It is not a documented replacement modern crypto persistence interface. [Client implementation](https://github.com/matrix-org/matrix-js-sdk/blob/develop/src/client.ts), [initializer](https://github.com/matrix-org/matrix-js-sdk/blob/develop/src/rust-crypto/index.ts), [WASM store](https://github.com/matrix-org/matrix-rust-sdk-crypto-wasm/blob/main/src/store.rs).

**Actual Node alternative:** the bot SDK's `RustSdkCryptoStorageProvider` takes a local directory and store type, persists bot device metadata, and its crypto client calls the Node binding with that path. The Node binding's current `OlmMachine.initialize` implementation opens a SQLite crypto store when configured with a path. This establishes an existing TS-accessible durable path, not production approval. [Bot storage provider](https://github.com/turt2live/matrix-bot-sdk/blob/main/src/storage/RustSdkCryptoStorageProvider.ts), [bot crypto initialization](https://github.com/turt2live/matrix-bot-sdk/blob/main/src/e2ee/CryptoClient.ts), [Node binding storage implementation](https://github.com/matrix-org/matrix-rust-sdk-crypto-nodejs/blob/main/src/machine.rs).

Important integration evidence: the bot SDK currently requests `@matrix-org/matrix-sdk-crypto-nodejs` `^0.4.0`, while the inspected binding source is mutable main. Do not assume their APIs, supported stores or security fixes align; pin the resolved release pair and run interoperability/restart/device-verification tests. Its initializer supplies an empty passphrase: filesystem persistence alone is not an established at-rest protection strategy. Evaluate supported unlock configuration or another maintained adapter without inventing encryption assurances. [Bot package manifest](https://github.com/turt2live/matrix-bot-sdk/blob/main/package.json).

A browser/Electron-style persistent profile is another TS reuse option if a desktop connector is acceptable; it trades packaging/runtime weight for an actual browser storage implementation. A bare Node `fake-indexeddb` shim is not evidence of durable storage and is not the proposed solution. No maintained drop-in durable Node adapter for the modern `matrix-js-sdk` WASM store was established in this review. That finding narrows the experiment; it does not rule out TypeScript Matrix connectors.

Next proof: compare one TS Node connector with the existing native dependency against one TS browser client, preserving device identity through restart and reconnect. In parallel with delivery feasibility, compare the endpoint work required by a Netlify relay + MLS WASM core. Select the path on total ownership cost and demonstrated user workflow; do not reject Netlify merely because an endpoint requires persistence, and do not move endpoint keys into Functions to make serverless execution convenient.

## What MLS supplies (conditional alternative research)

[MLS, RFC 9420](https://www.rfc-editor.org/rfc/rfc9420.html) defines authenticated group encryption and epoch transitions. Membership changes require committed updates; a server account removal is not a cryptographic removal. Added devices ordinarily receive the new epoch, not old history. The application must coordinate competing commits, persist group state, and avoid merging a locally generated commit until acceptance is established. KeyPackages require a single-use lifecycle. These requirements apply independently to each encryption audience in the proposed design.

The [MLS architecture, RFC 9750](https://www.rfc-editor.org/rfc/rfc9750.html) separates authentication and delivery services from clients. Khala's relay should deliver ciphertext and public admission material without holding endpoint secrets. MLS does not supply the invitation UI, transcript database, agent ownership policy, attachments, or recipient review workflow.

If the Netlify-native relay path is preferred after the substrate comparison, evaluate OpenMLS via TypeScript/WASM endpoints; a native owner connector is an alternative requiring separate agreement. Compare mls-rs if binding or persistence friction is lower. This is a prototype preference, not a finding that either engine meets Khala's production requirements. Avoid release-version pins copied from historical reports; inspect exact crates, bindings, crypto providers, licenses and audit scope during the experiment. Do not implement new crypto in TypeScript just to simplify the web stack.

## Keys, persistence and recovery

Private group state lives on authorised human devices and agent delivery endpoints. In the strict separate-audience design, agents never get the human review group's state; the simpler connector-gated variant trusts the connector with pending plaintext. Protect persisted state with device/OS storage facilities; do not put raw keys in app logs, crash telemetry or browser localStorage. An encrypted browser database still needs a meaningful unlock/key-management design.

Crypto state must not roll back on crash or backup restore. Serialise operations per local group and atomically checkpoint state, pending outgoing bytes and acceptance status. If a response is lost, query the immutable ciphertext command by ID before resending or discarding the pending commit. A rejected MLS commit must be reconciled using the selected library's pending-commit workflow; generating unrelated new bytes under a reused transport ID is invalid.

A revoked instance is removed from all its delivery audiences. Re-pairing creates a new device identity; do not silently restore access under the old label. Recovery should offer device-to-device enrolment or a user-held encrypted backup. Khala must not possess an escrow recovery secret if the promise excludes Khala from plaintext. Recovery of old crypto state is sensitive to forward-secrecy goals and stale-ratchet reuse; review it separately from transcript retention.

Attachments need client-generated object keys and client-side authenticated encryption. Put their keys and authenticated manifests inside the approved audience ciphertext. The model-facing adapter must not expose unreleased attachment keys/content through previews, link unfurling, search, export or notification APIs. The approved trusted connector may already possess those keys as a room endpoint; no cryptographic exclusion from that connector is promised.

## What the UI can verify

Show human identities, agent owners, authorised devices, and the actual encryption audience. Make device/instance changes visible before release. Support comparison of verified identity/group state between participants; a checkmark supplied solely by the relay cannot protect against its key substitution. Human admission and agent pairing are separate decisions.

The browser is itself an endpoint. A relay operator who can deliver modified JavaScript may steal plaintext at the browser even when the stored transcript is encrypted. Platform-blind storage is achievable; resisting an actively malicious application distributor needs independently verifiable client distribution and an additional trust design.

## Honest confidentiality claim

Suggested product wording: “Messages are encrypted between authorised participant devices and owner-controlled agent connectors. Khala's delivery service does not have message decryption keys. Messages released to an agent may be shared with that agent's configured model provider and authorised tools.” This wording is conditional on verifying the implementation and deployment.

Hosted inference does not erase delivery E2EE; it adds a downstream plaintext disclosure by an authorised endpoint. Therefore “only these four actors can read it” is inaccurate when a connector sends text to a model provider. A model provider's retention promise is not cryptographic exclusion. Local inference narrows that disclosure; confidential inference introduces attestation and software-policy dependencies. Neither should be required merely to demonstrate Khala's relay encryption.

Display the connector operator, inference destination, and declared downstream processing before pairing/release. Avoid asserting that remote agents are confined by policy merely because their owners declared it. A recipient can always copy plaintext once authorised. Encryption protects the delivery boundary, not against authorised recipients disclosing content.


## Airlock options and plaintext custody

Both options can keep Khala's relay blind to message bodies. They differ in which owner endpoint is trusted before release; neither prevents an authorised human from copying plaintext.

| Question | Connector-enforced review | Separate encryption audiences |
|---|---|---|
| Pending plaintext available to | Human devices and trusted owner connector | Human review devices and any explicitly authorised review gateway |
| Agent/model gets | Only content the connector releases through its harness API | Only ciphertext/plaintext in its own delivery audience |
| Compromised connector | Can bypass its own review policy and disclose pending text | Delivery-only connector cannot decrypt pending review content |
| Unattended automatic mode | Connector can forward while browsers sleep | Requires an online review/forwarding endpoint with review keys |
| Implementation cost | Fewer groups and forwarding steps; strong process/API boundary still needed | Multiple membership/state machines, projection, forwarding, recovery and rekeying |
| Honest claim | “Review controls what our connector passes into the agent context” | “This delivery endpoint lacks keys to unreleased content” |

A single encrypted room containing trusted connectors is a valid candidate for the first column. A connector must expose only released content to the agent's tools, file paths, logs and context interfaces. Running it alongside an unrestricted coding agent under the same OS account does not give strong isolation: that agent may read the connector's database, inspect its process or call its administrative API. Either accept this owner-host trust assumption or place review keys across a real process/user/VM boundary with authenticated narrow IPC. Secret storage alone does not fix unrestricted read access while the process is unlocked.

Decision: the user accepted connector enforcement. If Matrix is selected, use a shared encrypted Matrix room and enforce releases at the trusted connector; a Netlify-native relay must preserve the same endpoint policy. Separate audiences are a future option only if the promised boundary changes; do not make their complexity or browser-online requirement a baseline acceptance gate.

## Optional stricter topology: submission, review and delivery

The strict design requires three logical paths, even if submission and delivery reuse one owner-local group in a prototype:

1. **Submission:** an agent encrypts its outbound original to its owner audience. Its owner review client/gateway republishes the original into the human review audience. A normal non-member agent cannot send MLS application messages into the human group simply by being labelled an external sender; external proposals concern group changes, not an arbitrary write-only application channel. [MLS external proposals](https://www.rfc-editor.org/rfc/rfc9420.html#section-12.1.8).
2. **Review:** authorised human devices see the common transcript, including originals, and hold review keys. No delivery-only agent has these keys. A human joining later sees only explicitly transferred history; “both humans see the whole channel” requires product agreement on this history transfer.
3. **Delivery:** the recipient's review endpoint encrypts the approved original or derived bytes into that agent's audience. The release carries provenance and target bindings from [identity and policy](04-identity-trust.md). The relay stores opaque records and cannot produce missing plaintext bridges.

An automatic forwarding gateway becomes a review endpoint and must be shown as such during enrolment. If it joins a shared human review group it can read all content in that group, including messages unrelated to its chosen automatic peer. Scoped auto-release policy limits forwarding, not that gateway's decryption capability. Narrower custody requires more granular encryption audiences; do not advertise per-peer cryptographic isolation from a gateway holding the whole review group's keys.

Browser-only strict mode cannot promise unattended progress: pending outbound submissions and inbound releases wait while the relevant review endpoints are offline. Show `waiting_for_owner_endpoint`, distinct from `waiting_for_review`, and explain it before pairing. An owner-operated always-on gateway changes availability without giving the relay keys; a Khala-operated plaintext gateway changes the confidentiality promise.

## Browser/connector MLS feasibility gate (conditional alternative)

The OpenMLS upstream README explicitly places WASM among targets built but not tested on CI. The `js` feature allows compilation; it is not evidence of a working browser persistence or secure distribution solution. [OpenMLS platform matrix](https://raw.githubusercontent.com/openmls/openmls/main/README.md).

The alternative mls-rs advertises WASM and configurable storage, marks Web Crypto and Rust Crypto provider capabilities experimental in its table, and says the library has not had a full third-party security audit. Select and assess the exact provider/ciphersuite rather than treating “Rust” or “RFC conformant” as production readiness. [mls-rs README](https://raw.githubusercontent.com/awslabs/mls-rs/main/mls-rs/README.md).

Bound the experiment to browser plus TypeScript owner-connector endpoints, one required ciphersuite, one pinned library commit/version, and the four-actor flow. Deliver reproducible results for:

- creation, offline admission, membership removal and selected-history import across the two builds;
- persistent browser storage, blocked storage, quota failure, refresh and two tabs attempting the same group mutation;
- concurrent membership commits, lost acceptance responses, rejected commits and restart during encryption/checkpoint;
- duplicate/out-of-order frames, delayed epochs, offline catch-up and explicit irrecoverable-state handling;
- capture of all recipient-agent keys plus relay ciphertext: unreleased decryption fails only in the strict variant, and the simpler variant is labelled accurately;
- build feature audit: sensitive-content/key debug features disabled in shipped artefacts, dependency/provider versions and any relevant audit coverage recorded.

Use one worker/owner per device's live group state and serialize mutation. Treat local database transactions, the MLS provider's writes, and relay acceptance as separate boundaries that the experiment must reconcile; do not assert a transaction spans them. OpenMLS continuously persists group changes through its provider and trusts restored state. Its deletion requirements also mean append-only snapshots and retained backups can defeat expected key erasure. [OpenMLS persistence guide](https://book.openmls.tech/user_manual/persistence.html).

## Recovery, history and unattended custody decisions

Separate three products: restoring account login, adding a new cryptographic device, and recovering retained transcript content. Account recovery alone must not silently confer old message decryption. Device-to-device enrolment can authorise a new device with fresh state and an explicit history package. If all devices/backup secrets are gone, truthful outcomes include unrecoverable old history; decide whether that is acceptable before promising recovery.

Do not restore a cloned active ratchet snapshot into two simultaneous writers. Restore retained transcript data separately from fresh group enrolment where possible. If crypto-state backup is supported, specify anti-rollback/rejoin behavior, key retirement and the weaker historical secrecy caused by retained secrets. Browser IndexedDB, native SQLite and OS keychain choices each need operational proof; encryption at rest without a defined unlock secret is incomplete.

An unattended connector needs an unlock strategy: interactive unlock after restart, device-bound secret available at boot, or an external owner-controlled secret service. Each shifts either availability or host-compromise exposure. Do not silently put the secret in a Khala account recovery service. Document operator, filesystem/process access, backup scope, telemetry, model destination and removal behavior for each endpoint.

A proof of confidential computing would additionally need fresh attestation, accepted software measurement and TCB policy, a channel bound to the measured workload, and controlled plaintext egress. Defer it unless the product explicitly needs to run connectors on an untrusted operator. A vendor's attestation or retention marketing cannot establish those properties for Khala's deployment. The recovered reports' numerical attack/retention claims have not been accepted as planning facts; see [evidence status](08-security-evidence.md).
