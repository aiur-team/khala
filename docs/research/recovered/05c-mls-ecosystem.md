## 1. Production deployments

**The picture changed in May 2026.** Until then MLS was one enterprise messenger plus one Cisco meetings feature. Now it is the interop layer for carrier-scale consumer RCS, which is the largest MLS deployment in existence.

**RCS (Apple + Google, GSMA Universal Profile) — shipped, beta, carrier-scale.** GSMA announced on 14 March 2025 that RCS Universal Profile 3.0 adds E2EE "based on the Messaging Layer Security (MLS) protocol" and would be "the first large-scale messaging service to support interoperable E2EE between client implementations from different providers" (https://www.gsma.com/newsroom/article/rcs-encryption-a-leap-towards-secure-and-interoperable-messaging/). UP 3.1 (25 July 2025) added onboarding and xHE-AAC, no new E2EE content (https://www.gsma.com/newsroom/article/elevating-the-messaging-experience-with-rcs-universal-profile-3-1/). UP 4.0 (26 March 2026) said E2EE was "being tested between Android and iOS devices" (https://www.gsma.com/newsroom/article/from-rich-text-to-video-rcs-universal-profile-4-0-has-arrived/). It shipped 11 May 2026: Apple's newsroom announced "End-to-end encrypted RCS messaging begins rolling out today in beta" with iOS 26.5, a lock icon, and auto-enablement "over time for new and existing RCS conversations" (https://www.apple.com/newsroom/2026/05/end-to-end-encrypted-rcs-messaging-begins-rolling-out-today-in-beta/); Google's matching post is https://blog.google/products-and-platforms/platforms/android/android-ios-end-to-end-encrypted-rcs-messaging/ and GSMA's is https://www.gsma.com/newsroom/press-release/ios-26-5-brings-e2ee-for-rcs-a-new-milestone-for-secure-cross‑platform-messaging/. Apple's carrier matrix already lists "End-to-end encrypted RCS messaging (beta)" for AT&amp;T, T-Mobile, Verizon, US Cellular, FirstNet, Mint, Visible, Xfinity, Spectrum, Boost, Consumer Cellular and the major Canadian carriers (https://support.apple.com/en-us/109526). UP 4.1 (28 July 2026) says E2EE is "now rolling out" and its headline change is refinement of the E2EE spec "based on lessons from extensive interoperability testing" plus a gRPC connectionless transport (https://www.gsma.com/newsroom/article/rcs-universal-profile-4-1-stronger-foundations-for-secure-messaging/). ## 4. Membership churn mechanics (RFC 9420, https://www.rfc-editor.org/rfc/rfc9420.html)

**State model.** A group lives in a sequence of epochs; each epoch has a GroupContext (group_id, epoch, tree_hash, confirmed_transcript_hash, extensions — §8.1) and a key schedule derived from the previous epoch's init_secret plus a fresh commit_secret (§8). Membership is a left-balanced binary ratchet tree whose leaves are clients (§4, §7). The tree invariant (§16.2): a node's private key is known only to members whose leaves are in its subtree. That is what lets a member encrypt to everyone-but-one with log(N) ciphertexts instead of N−1 (§4: "log(N) encryptions to subtrees, instead of the N-1 encryptions"). Nodes can be blank; a blank node's resolution is the set of non-blank nodes below it (§4.1.1), and parent nodes carry an `unmerged_leaves` list of leaves added beneath them since the node was last refreshed (§7.1).

**KeyPackages (§10).** To be added asynchronously a client pre-publishes KeyPackages: protocol version, ciphersuite, an HPKE `init_key` used only to encrypt a Welcome, and the LeafNode (encryption key, signature key, credential, capabilities, lifetime) that will be placed in the tree; the whole thing is signed (§10). KeyPackages are single-use — reuse enables replay (§16.8) — except a designated "last resort" package, formalized as a component in draft-ietf-mls-extensions-10 §6.4 (https://www.ietf.org/archive/id/draft-ietf-mls-extensions-10.html). The DS acts as the KeyPackage store and should delete on fetch (RFC 9750 §5.1, https://www.rfc-editor.org/rfc/rfc9750.html).

**Proposals (§12.1).** Add carries a KeyPackage; on application the new member goes in the leftmost blank leaf (or the tree doubles, §7.7), and its index is appended to `unmerged_leaves` on every non-blank ancestor — the new leaf cannot yet know those ancestors' secrets (§12.1.1). Update replaces the sender's own LeafNode and blanks its direct path (§12.1.2). Remove blanks the target leaf and its direct path, then truncates the tree from the right if the rightmost subtree is empty (§12.1.3). Also PreSharedKey, ReInit, ExternalInit, GroupContextExtensions (§12.1.4–7). Proposals may be sent by a non-member if the group's `external_senders` extension pre-provisions their signature key — the RFC's own example is "an automated service might propose removing a member of a group who has been inactive" — and external senders may only send add, remove, psk, reinit, group_context_extensions (§12.1.8). Proposals do nothing until committed.

**Commit (§12.4).** A Commit references proposals (by hash or inline) and applies them in a fixed order — GroupContextExtensions, then Updates, then Removes, then Adds in list order, then PSKs, ExternalInit, ReInit (§12.3). A "full" Commit also carries an UpdatePath (§7.6): the committer generates a fresh leaf key pair, derives a chain of path secrets up its direct path, and for each node in the path encrypts the path secret to the resolution of the sibling subtree (HPKE). The number of ciphertexts is the sum of resolution sizes along the path — log(N) in a healthy tree, degrading toward N as more nodes are blanked. The root path secret becomes commit_secret, feeding the new epoch's key schedule. Path-less Commits are permitted only when no proposals require it (any Remove, Update, ExternalInit, GroupContextExtensions, or empty Commit forces a path, §12.4). Creating a Commit MUST NOT modify sender state until it is known to be accepted (§14).

**Epoch transition and TreeKEM cost.** Processing a Commit: verify, apply proposals, decrypt the one UpdatePath ciphertext in your resolution, derive path secrets upward from there, recompute tree hash and parent hashes (§7.8, §7.9), advance the key schedule, verify the confirmation_tag. Every member must do this for every Commit. Work is O(log N) HPKE decryptions but O(N) hashing/validation over the tree — which is exactly what the measurements in §5 below show dominating.

**Welcome and joining (§12.4.3.1).** The committer produces a Welcome for the members it added: GroupInfo (GroupContext + extensions + confirmation_tag + signer) encrypted under a key derived from joiner_secret, and joiner_secret plus the path secret of the lowest common ancestor HPKE-encrypted to each new member's init_key (GroupSecrets). One Welcome can serve many joiners. By default GroupInfo carries only the tree_hash, and the joiner must obtain the tree "from some other source (for example, the DS might provide a cached copy)" — integrity is guaranteed by the hash so the source need not be trusted; alternatively the full public tree is inlined via the `ratchet_tree` extension (§12.4.3.3), which is 2^(d+1)−1 nodes and the dominant size cost at scale. draft-ietf-mls-ratchet-tree-options-01 exists precisely to standardize the out-of-band options because the extension "scales roughly linearly" with group size (https://www.ietf.org/archive/id/draft-ietf-mls-ratchet-tree-options-01.html). The joiner cannot decrypt or verify the Commit that added it; it receives post-Commit state only.

**What a joiner can read.** Only the epoch it joined and later. It receives the joiner_secret and one path secret; it never receives prior epoch secrets, so history is opaque (RFC 9750 §6.1: "Messages sent before a client joins or after they are removed are protected with keys that are not accessible to the client"). It does receive the full public tree — every member's LeafNode with credential and public keys — so group membership metadata is fully visible to joiners (§16.4.3).

**What a leaver can read.** A removed member sees the Commit that removes it (it is in the old epoch) but the UpdatePath encrypts to resolutions that exclude its leaf and its blanked direct path, so it cannot derive commit_secret and is locked out of epoch n+1 onward. "Compromise of a member removed from a group does not affect the security of messages sent after their removal" (RFC 9750 §6.1). Crucially, there is no unilateral leave: "There is no similarly unilateral way for a member to leave the group; they must be removed by a remaining member" (RFC 9750 §6.1). A member can only send a Remove proposal for itself and wait; external-commit joiners ignore pending proposals so it may have to re-propose every epoch — the SelfRemove proposal in draft-ietf-mls-extensions-10 §6.3 exists to fix exactly this. Application messages within the epoch a leaver was still in remain readable by it; secrets it already derived are protected only by its own deletion discipline.

**External joins (§3.3, §12.4.3.2, §8.3).** A non-member can add itself via an external Commit if it has a GroupInfo with the `external_pub` extension. It HPKE-exports a new init_secret to `external_pub` (§8.3), places an ExternalInit proposal plus its own leaf in a full Commit at the leftmost free leaf, signs with its own key, and sends with sender type `new_member_commit`. Constraints: MUST carry a path, MUST NOT reference proposals by hash, MAY include a Remove of its own prior leaf ("resync" flavor, which the RFC warns lets a stolen signature key evict the legitimate device in one step). Each GroupInfo is single-use because the join advances the epoch, so the DS must republish GroupInfo every epoch. Existing members need no interaction — but the joiner must parse the entire tree to build its path, which is the slowest operation measured at scale (§5).

**FS vs PCS (§16.6, RFC 9750 §8.2.2).** Forward secrecy between epochs comes from deleting old tree private keys; within an epoch from the secret tree's per-sender ratchets and the deletion schedule (§9.2) — keys are deleted once used. Post-compromise security comes only from a Commit with a path being processed: "sending an Update proposal does not achieve PCS until another member includes it in a Commit," and the guarantee holds "when the members of the group process the relevant Commit, not when the sender creates it." Both properties are undermined by offline members holding old keys; the RFC says applications "SHOULD have mechanisms for evicting group members that are offline for too long," and RFC 9750 recommends mandating updates from idle clients. Healing is per-group; PSK export (§8.4) can carry PCS across groups (RFC 9750 §6.2).

**Concurrent commits and DS serialization (§14; RFC 9750 §5.2).** Two members committing from the same epoch produce incompatible successor states. RFC 9420 §14: "Applications MUST have an established way to resolve conflicting Commit messages for the same epoch," either preventing conflicts or choosing a canonical one; forked states must be discarded promptly for FS; the committer MUST NOT apply its own Commit until accepted; the Welcome "MUST NOT be delivered to a new joiner until it's clear that the Commit has been accepted"; and "in a sufficiently busy group, a given member may never be able to send a Commit message because they always lose." RFC 9750 §5.2 frames this as CAP: a strongly consistent DS acts as an ordering server that "is trusted to break ties," letting clients apply the first valid Commit per epoch and ignore the rest, optionally rejecting redundant Commits proactively; the risk (§5.3) is the DS advancing its own epoch counter on a Commit that clients reject, leaving the group stuck, and recovery via external join trusts a DS-served GroupInfo and can be abused to undermine PCS. Proposals must arrive before the Commit referencing them; application messages tolerate reordering via generation counters (§15.3) but implementations must cap how far they ratchet forward to avoid DoS. Welcomes must be coupled to the tie-break (RFC 9750 §5.2.3).

**Cost of churn, from the mechanics.** Each join or leave is one Commit: every member does O(log N) HPKE plus O(N) tree hashing and validation, and the committer also produces a Welcome whose size is O(N) if the tree is inlined. Batching many proposals into one Commit amortizes this (proposals are cheap, the Commit is the expensive unit). Frequent Removes and Updates blank nodes; a tree where only one party ever commits degenerates toward N ciphertexts per Commit (§4's log(N) is the healthy case, and the 70–80× penalty in §5 below is the pathological one). Latency of a membership change is bounded below by DS round-trip plus every recipient's processing, and any join must wait until the Commit is confirmed before the Welcome is released. draft-ietf-mls-partial-02 attacks the join side only: Join O(N)→O(log N), Process Commit stays O(N), and it concedes it "does not address the potentially linear scaling of Commit messages; in fact, it makes Commits slightly bigger" (https://www.ietf.org/archive/id/draft-ietf-mls-partial-02.html).

## 5. Scaling — concrete published numbers

The standards give asymptotics only: RFC 9420 says "groups in size ranging from two to thousands" and "costs that scale as the log of the group size"; RFC 9750 aims at "tens of thousands of members"; Partial MLS motivates with "meetings with a thousand or more participants" and gives only Big-O; ratchet-tree-options says only that the extension "scales roughly linearly." None of OpenMLS (one two-member Criterion bench, https://book.openmls.tech/ has no numbers), mls-rs (benches at group sizes 16/64/128 in `mls-rs/src/test_utils/benchmarks.rs`, no published results), or MLSpp (no benches) publish figures. draft-ietf-mls-pq-ciphersuites-06 defines 11 PQ/hybrid suites and gives no size or performance numbers. No vendor (Cisco, Wire, Google, Meta) has published a measurement report — not found.

**The one real at-scale measurement.** Soler et al., "Analysis of Efficiency of the Messaging Layer Security protocol in Experimental Settings," arXiv:2502.18303v2 (Feb 2026), code at https://github.com/SDABIS/mls_experimental_analysis (https://arxiv.org/abs/2502.18303v2). 10,000 OpenMLS clients on a 16-core/128 GB VM, MQTT+HTTP DS, 60/20/20 add/update/remove. Finding: "the overall scaling of MLS's performance is linear, which contradicts the theoretical results which point to logarithmic performance." Commit size ~1–3.5 KB at 100 members, 2–8 KB at 750, 10–40 KB at 5,000; per-update message size stays ~2–10 KB across 0→10,000 with step jumps at 4,096 and 8,192 (tree doubling). Commit generation 2–6 ms at 100, 40–65 ms at 5,000, ~100 ms at 10,000; processing 1.8–2.2 ms at 100, 30–50 ms at 5,000, ~0.1 s at 10,000 ("if executed sequentially, it takes more than 15 minutes for all members to process it"). External Join generation 3–3.5 s at 10,000 — roughly 30× a commit — because the joiner parses the whole tree; Commit+Welcome costs about the same. Welcome and GroupInfo (with inlined tree) reach ~2–2.5 MB at 10,000 members. Degenerate tree where one member always commits: ~700–800 KB per commit at 10,000 vs ~10 KB healthy, a 70–80× penalty — directly relevant to admin-only-commit designs. Cryptography is only 1% (healthy) to 10% (degenerate) of cost; storage, tree hashing, validation, and Welcome construction — all linear — dominate. Max DS latency ~300 ms at 10,000. Prior measured group sizes in the literature were 128 (Weidner, Balbás) and 1,000 (Chevalier).

**Wire-size and state tables.** SUMAC, eprint 2025/682 (https://eprint.iacr.org/2025/682), Table 4, plain TreeKEM per-user bytes: add-user 800 B at 16 members, 1,156 B at 256, 1,920 B at 65,536 classical; 18,178 / 27,001 / 45,489 B post-quantum (~23× PQ blow-up). Remove 538 / 899 / 1,664 B classical. Table 1, per-user state: 2.0 kB / 26.4 kB / 6.3 MB classical, 56 kB / 670 kB / **158 MB** PQ at 65,536 — the starkest published memory figure. Add-commit generation 2 ms at 16, 11 ms at 256, 117 ms at 1,024. "The Art of Bonsai," eprint 2024/746 (https://eprint.iacr.org/2024/746): proposals range 52 B (remove) to 3.2 kB (PQ add); tree-dependent cost is 14–83% of an add commit; HPKE sizes pk/ct in bytes — X25519 32/80, P-256 65/113, ML-KEM-768 1,184/1,168, ML-KEM-1024 1,568/1,648, Classic McEliece 6688128 1,044,992/288; binary trees are optimal classically, ternary for PQ; TreeKEM's left-balanced evolution costs 4–7% over an ideal tree. Hashimoto et al., eprint 2021/1407 (https://eprint.iacr.org/2021/1407): TreeKEM total commit bandwidth is Ω(N log N); on an M1 lattice CmPKE encrypts to 2^10 recipients in &lt;100 ms. Hale et al., eprint 2026/034 (https://eprint.iacr.org/2026/034): PQ ciphersuites in OpenMLS produce 10–35× more bytes over 500 epochs (0.24–0.44 MB classical vs 1.4–8.4 MB PQ) but only at group size 2. XMTP's only hard number is the code limit MAX_GROUP_SIZE = 250 with ~105 KB per-member payload budget.

**Not found:** measured RSS of a real client by group size (only analytical SUMAC and 2-member Hale figures); any production-vendor benchmark; concrete byte counts in any of the six active WG drafts. The asymptotic security papers (Bienstock–Dodis–Rösler 2020/1171, Alwen et al. server-aided 2021/1456, DeCAF 2022/559, Grafting Key Trees 2021/1158, TreeSync 2022/1732) exist but yield no scaling measurements.

## 6. Non-human members, bots, agents

Almost nothing exists, and the one thing people reach for is the wrong tool. draft-ietf-mls-virtual-clients-01 (https://datatracker.ietf.org/doc/draft-ietf-mls-virtual-clients/, 2026-07-06, repo pushed 2026-08-27) is about N cooperating clients sharing one leaf — multi-device for one human, performance, metadata hiding. It never mentions bots or agents; its open issues are PPRF mechanics and "find a better name."

The only adopted WG treatment of non-human members is in MIMI, not MLS: draft-ietf-mimi-room-policy-04 §6.7 "Chat bot policy component" (https://datatracker.ietf.org/doc/draft-ietf-mimi-room-policy/) defines a `bot_policy` MLS component (§10.1.12) with a `Bot` struct: name, description, homepage, `local_client_bot` (bot is not a member, sees content only via a human's client), `bot_role_index` (bot slots into the normal role/permission framework; 0 = not a participant), `can_target_message_in_group` (uses MLS Targeted Messages from draft-ietf-mls-extensions §2.2 to DM one user inside a group), and `per_user_content` (explicitly permits divergent content per recipient — "a poker bot could deal a different hand to each user"). draft-ietf-mimi-protocol-06 has no bot concept; bots are ordinary MLS leaves with ordinary credentials differentiated only by policy. There is no bot-specific credential type and nothing at the MLS layer distinguishing a machine leaf from a human one. RFC 9420 §12.1.8's `external_senders` mechanism is the closest native primitive: a pre-provisioned non-member signer that can propose adds/removes (e.g. an inactivity-eviction service) but cannot read anything.

AI agents specifically: exactly one draft, individual, unadopted — draft-chapman-a2a-mls-03, "End-to-End Encryption and Purpose-Bound Governance for Agent-to-Agent Messaging," Luke Chapman/Qwixl (https://datatracker.ietf.org/doc/draft-chapman-a2a-mls/), -00 through -03 all between 2026-07-28 and 2026-08-01, no WG, no list discussion. It binds the MLS LeafNode `signature_key` to an Ed25519 `did:key` agent identity, mandates ciphersuite 0x0001, adds signed "Governed Object" envelopes (payload + purpose + expiry) as application messages, and binds to the A2A protocol. Sole implementation is the author's https://github.com/Qwixl/Atom (0 stars). Neighbouring agent drafts (draft-gebauer-iacp-03, draft-tonyai-a2a-trust-03) do not use MLS. `gh search code "rfc 9420 agent"`, `"VirtualClient mls"`, and MLS+MCP searches all return zero; no mlswg repo has an issue mentioning bot/agent/non-human; the mailarchive search endpoint returns 403, but the visible 2026 MLS list window (two-party profile adoption, IETF 126 minutes, Partial MLS PRs, "Make WireFormats Sane Again") contains no such thread. The open territory — machine-identifiable credentials, attested capability, human-to-agent delegation, agent key lifecycle — is unwritten.
