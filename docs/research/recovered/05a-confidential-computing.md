# Confidential computing for a key-holding server-side agent: state of the world, September 2026

**Method note.** This session's web-search budget was exhausted almost immediately, so everything below was built from direct fetches of primary sources (vendor docs, spec PDFs, NVD/Intel/NVIDIA advisories, IETF datatracker, GitHub via API) rather than search. Claims I could not re-verify live are flagged. AMD's own site timed out repeatedly, so AMD bulletin claims are triangulated through NVD.

## 0. The short answer

Yes, with big asterisks. A remote relying party outside the cloud account can today cryptographically verify that *a genuine AMD/Intel TEE, at a specific firmware/microcode patch level, launched an exact measured image, and holds a fresh ephemeral key bound to that report*. That is a real, verifiable, hardware-rooted claim, and it is enough to build "release the group key only to this measured code" if you wrap it in RA-TLS/HPKE and pin the measurement yourself.

What it does **not** give you, out of the box, from any hyperscaler: proof that the measurement corresponds to auditable source (you need reproducible builds + a transparency log, which only Apple PCC, WhatsApp Private Processing, and a couple of startups actually ship); protection against an operator who redeploys a different image tomorrow (needs the same log plus a client that refuses unlisted measurements); protection against physical DRAM-bus interposers, which in 2025-26 were shown to **forge attestation outright** on SGX/TDX/SEV-SNP and which both Intel and AMD have declared out of scope; and any assurance about what the code does with the key after release. The GPU side (required for LLM inference) is real on H100 but composite CPU+GPU attestation is still stitched together by hand, not a standard.

## 1. AMD SEV-SNP

**What the report contains.** The `ATTESTATION_REPORT` (guest ioctl `SNP_GET_REPORT` via `/dev/sev-guest`, https://www.kernel.org/doc/html/latest/virt/coco/sev-guest.html) is ECDSA-P384-signed by the AMD Secure Processor and carries: `MEASUREMENT` (SHA-384 launch digest), `REPORT_DATA` (64 caller bytes: your nonce or hash of an ephemeral pubkey), `HOST_DATA` (64 host-chosen bytes folded into launch), `ID_KEY_DIGEST`/`AUTHOR_KEY_DIGEST` (guest-owner keys that signed the expected launch digest via the ID block, so the *owner* can assert "I approved this measurement" independent of the platform), `POLICY` (debug/SMT/migration bits, min ABI), four TCB structs (current/committed/reported/launch, each with microcode/SNP-fw/bootloader/TEE SVNs), and `PLATFORM_INFO` (SMT, TSME, RAPL-disabled, alias-check-complete, ciphertext-hiding). Azure surfaces each as a JWT claim, e.g. `x-ms-sevsnpvm-idkeydigest`, `x-ms-sevsnpvm-is-debuggable`, `x-ms-sevsnpvm-microcode-svn` (https://learn.microsoft.com/en-us/azure/confidential-computing/guest-attestation-confidential-vms).

**What MEASUREMENT actually covers.** Exactly what `virtee/sev-snp-measure` computes (https://github.com/virtee/sev-snp-measure): the OVMF/firmware image, and with direct kernel boot the kernel + initrd + cmdline (via the OVMF kernel-hashes table), plus the initial VMSA of every vCPU (vCPU count and type change the hash). It is a **launch-time** digest of initial memory. It does **not** cover the root filesystem, anything loaded after boot, the application binary, or runtime state. To cover those you need a second, weaker chain: a vTPM at VMPL0 (Azure's and GCP's managed vTPMs, https://docs.cloud.google.com/confidential-computing/confidential-vm/docs/attestation; or open-source COCONUT-SVSM, https://coconut-svsm.github.io/svsm/, active but I could not confirm a GA milestone) with PCR-extended measured boot, or dm-verity of the disk image with its root hash baked into the measured cmdline/initrd (this last is what Tinfoil and Continuum do, and it's the cleanest way to pull "the whole OS image" into the hardware measurement).

**VCEK vs VLEK, KDS.** The report is verified against a leaf cert chained ARK → ASK → VCEK/VLEK. VCEK is derived on-chip from a per-chip secret *and* the reported TCB, fetched from AMD's KDS by chip ID + TCB (`snpguest fetch vcek`, https://github.com/virtee/snpguest). VLEK is an AMD-issued key leased to a cloud provider and loaded into the chip so relying parties don't learn a stable chip ID and KDS isn't hammered; `snpguest` supports both. GCP caches VCEKs on the VM rather than live-querying KDS, so a relying party who wants freshness must fetch from KDS itself. Because VCEK is TCB-derived, a firmware update automatically yields a new key; the *reported* TCB in the signed report is your anti-rollback anchor and the firmware refuses to run below the committed TCB. The verifier must enforce a **current** minimum-TCB policy (Constellation exposes this as a config knob, https://docs.edgeless.systems/constellation/architecture/attestation); stale policies silently keep accepting vulnerable firmware, and that is the most common real-world failure.

**Not attested.** Runtime memory content after launch (RMP is access control, not attestation); I/O devices and DMA (without TIO); interrupt delivery (now hardened guest-side, see below); ciphertext side-channels unless the ciphertext-hiding platform bit is checked; availability; anything below the Secure Processor.

**Attacks, current status (verified via NVD/CVE records):**
- **CacheWarp** CVE-2023-20592: fixed by firmware (per-generation "unaffected" versions listed at https://www.cve.org/CVERecord?id=CVE-2023-20592); verifiable via reported TCB.
- **WeSee / Heckler** (Ahoi attacks, https://ahoi-attacks.github.io/, arXiv:2404.03526): tracked as CVE-2024-25742 (#VC injection) and CVE-2024-25743 (interrupt 0/14 → signal-handler hijack, CVSS 7.1). Fixed in **guest kernel ≥6.9**, not silicon, so unpatched guest kernels remain exposed on fully patched hosts. Attestation only proves this if the kernel is in MEASUREMENT.
- **BadRAM** CVE-2024-21944 (https://badram.eu/): AMD added a boot-time alias check. **Battering RAM** (https://batteringram.eu/, embargo lifted Sept 30 2025) bypasses it with a $50 runtime DDR interposer, replays launch measurements, and breaks SEV-SNP attestation; neither AMD nor Intel patched, both declare physical interposers out of scope.
- **TEE.fail** (https://tee.fail/, IEEE S&P 2026): DDR5 interposer against SGX, TDX, **SEV-SNP (Zen 4/5)** and **NVIDIA H100/H200/B100/B200 CC**; extracts provisioning keys and forges quotes. Unpatched by design.
- **Voltage-glitch (Buhren-style):** no CVE; explicitly outside the threat model.
- **CipherLeaks-class ciphertext side channels:** newer silicon has ciphertext hiding but it is opt-in and only detectable if you check the PLATFORM_INFO bit.
- **CVE-2024-56161** (Google-found microcode signature bypass, CVSS 7.2): patched Dec 2024, disclosed Feb 2025 (http://www.openwall.com/lists/oss-security/2025/02/04/1); Debian notes SEV firmware/BIOS updates were also required on some platforms to restore attestation integrity.
- **2025-2026 stream:** CVE-2025-0033 (RMP write during SNP init, Oct 2025), CVE-2025-29948 (RMP bypass on Turin, Feb 2026), CVE-2025-29934 (stale TLB, Nov 2025), CVE-2025-29943 (SNP guest stack pointer corruption, Jan 2026), and **CVE-2025-61972** (CVSS 8.5, May 2026: missing NBIO lock → arbitrary SMN access → **code execution in the ASP itself**, i.e. the root that signs your reports; https://services.nvd.nist.gov/rest/json/cves/2.0?cveId=CVE-2025-61972). Five bulletins in eight months on current-gen silicon. This is a platform still being hardened, not a settled one.

**Verdict.** SEV-SNP attestation is cryptographically sound for its narrow claim and bugs get patched in ways you can verify via TCB. A remote relying party can verify with `snpguest`/`sev-snp-measure` and a pinned ARK, with no cloud-account relationship. They still trust AMD's root and patch cadence, their own minimum-TCB discipline, the operator for everything outside RMP (I/O, scheduling, side channels), and physical security absolutely.

## 2. Intel TDX

**Measurement registers** (TDX Module spec, https://cdrdv2-public.intel.com/733568/tdx-module-1.0-public-spec-344425005.pdf). **MRTD** is built by the TDX module during `TDH.MEM.PAGE.ADD`/`TDH.MR.EXTEND`, sealed by `TDH.MR.FINALIZE`; it covers the initial pages the loader chose to extend (virtual firmware and, with direct boot, kernel/initrd). **RTMR0-3** are zero at launch and extended by the *guest* via `TDG.MR.RTMR.EXTEND`, PCR-style; the de facto convention (td-shim/OVMF/Linux, https://docs.kernel.org/arch/x86/tdx.html) is RTMR0 = firmware config, RTMR1 = kernel, RTMR2 = cmdline+initrd, RTMR3 = application/agent-defined. That mapping is convention per boot stack, not hardware-enforced, so a verifier must know the specific stack. **MRCONFIGID/MROWNER/MROWNERCONFIG** are opaque owner-supplied labels with no cryptographic meaning. Not measured: userspace, the application, disk, runtime code loads, unless the guest deliberately extends RTMR3 (or uses dm-verity into the measured cmdline).

**Quote path.** `TDG.MR.REPORT` yields a `TDREPORT` MAC'd with a CPU-local key; the host passes it to the **TD Quoting Enclave**, an ordinary SGX enclave, which verifies via `EVERIFYREPORT2` and signs with its ECDSA-384 attestation key, certified by the PCE under the PCK cert chain to Intel's root. DCAP's `libsgx-dcap-quote-verify` verifies locally against collateral (TCB Info, QE Identity, CRLs) from a self-hosted PCCS syncing from Intel PCS (https://download.01.org/intel-sgx/latest/dcap-latest/linux/docs/Intel_TDX_DCAP_Quoting_Library_API.pdf). So yes, a third party outside the cloud account can verify a TDX quote with no Intel Trust Authority and no cloud credentials, needing only Intel's root and reasonably fresh collateral. Stale collateral silently accepts revoked TCBs.

**Module updates.** SEAMLDR can hot-reload the module without reset; CPU-level TCB recovery needs a reboot; PCE upgrade requires a new PCK cert. In practice Azure's DCesv6 TDX SKU lists "Memory Preserving Updates: Not Supported" (https://learn.microsoft.com/en-us/azure/virtual-machines/sizes/general-purpose/dcesv6-series), so TCB recovery still means a VM restart there.

**Intel Trust Authority** is alive, "now free to use for customers using TEEs on select cloud service providers" (Azure, GCP, IBM listed; AWS not), covers TDX and NVIDIA H100 attestation, and offers a release-key-on-token pattern (https://www.intel.com/content/www/us/en/security/trust-authority.html). Near AI and Secret Network integrated it in 2026. It's a convenience verifier, not a requirement; DCAP is the independent path.

**Attacks.**
- **TDXdown** (Wilke et al., CCS 2024; single-stepping and the "StumbleStepping" instruction-counting attack): Intel added a single-step countermeasure in the TDX module but the counting variant was reported as unmitigated. **Not re-verified this session** (paper and Intel guidance pages 404/403'd); treat as prior knowledge.
- **WireTap** (https://wiretap.fail/, CCS 2025): DDR4 interposer extracted the QE's signing key on 3rd-gen Xeon SGX and forged quotes; demonstrated breaking Secret Network, Phala, Crust, IntegriTEE in production.
- **TEE.fail** (above): DDR5, 4th-gen+ Xeon, forges TDX quotes with garbage measurements that pass Intel's verifier. Unpatched by design.
- **Battering RAM**: TDX "potentially affected, limited demonstrated impact."
- **2025-26 CVEs**: INTEL-SA-01312 (Aug 2025, low), INTEL-SA-01436 (Aug 2026, CVE-2026-20885 CVSS 7.0 in the TDX module, fixed 1.5.29/2.0.17), INTEL-SA-01462 (guest software), and **INTEL-SA-01449 (Aug 2026, CVE-2026-20702, CVSS 8.9) in the DCAP Quote Verification Library** itself, fixed only in DCAP 1.25 (https://www.intel.com/content/www/us/en/security-center/advisory/intel-sa-01449.html). If you self-verify, you must be on QVL ≥1.25.
- Legacy SGX issues (Foreshadow/LVI/ÆPIC/Downfall) are mitigated but matter because the QE is SGX.

**Verdict.** Architecturally sound and independently verifiable with DCAP. You trust Intel's root and every module/microcode update, the SGX-based QE, verifier collateral freshness, and, as with AMD, physical security: interposer research now demonstrates *quote forgery*, not just leakage, and vendors have answered "out of scope."

## 3. AWS Nitro Enclaves

**Document.** CBOR/COSE_Sign1 (ECDSA-P384), fields `module_id`, `timestamp`, `digest` (SHA384), `pcrs`, `certificate`, `cabundle`, optional `public_key`/`user_data`/`nonce` ≤1024 B each (https://github.com/aws/aws-nitro-enclaves-nsm-api/blob/main/docs/attestation_process.md). Chain: AWS Nitro Enclaves Root-G1 (30-year) → regional/zonal intermediates → short-lived leaf. Leaf certs are short-lived, so offline verification of an old document requires having captured the chain and checking validity as-of the timestamp.

**PCRs** (https://docs.aws.amazon.com/enclaves/latest/user/set-up-attestation.html): PCR0 = whole EIF (kernel+cmdline+all ramdisks), PCR1 = kernel+cmdline+first ramdisk (bootstrap), PCR2 = application ramdisks, PCR3 = SHA384 of parent instance IAM role ARN, PCR4 = SHA384 of parent instance ID, PCR8 = signing cert of a signed EIF. PCR3/4 are operator-controlled context, useful for the account owner's KMS policy, useless to an outside verifier. PCR0/1/2 are what an outsider pins. Debug-mode enclaves report all-zero PCRs. Formula: `PCRx = sha384(48 zero bytes || content)` per https://github.com/aws/aws-nitro-enclaves-image-format.

**KMS.** `Decrypt`, `DeriveSharedSecret`, `GenerateDataKey`, `GenerateDataKeyPair`, `GenerateRandom` accept a `Recipient` attestation document and return plaintext encrypted to the enclave's `public_key`; key policies use `kms:RecipientAttestation:ImageSha384` and `:PCR0`-`:PCR8` (https://docs.aws.amazon.com/kms/latest/developerguide/cryptographic-attestation.html, https://docs.aws.amazon.com/kms/latest/developerguide/conditions-attestation.html). **This is enforced by KMS inside the account.** A third party cannot see the key policy, cannot prove it wasn't edited after they checked, and gains nothing from it unless they own the KMS key. What a third party *can* do is receive the attestation document over the wire, verify the AWS chain and PCRs themselves, and encrypt to `public_key`; KMS is irrelevant to that path. New in 2025: the same KMS conditions work for **NitroTPM + Attestable AMIs** on full EC2 instances (https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/nitrotpm-attestation.html), which AWS pitches for "isolate data from your own operators."

**Reproducible builds.** `nitro-cli build-enclave` (v1.5.0, Aug 13 2026, actively maintained) ingests a Docker image, so PCR0 inherits Docker layer nondeterminism; the EIF spec defines determinism only in terms of section order and says nothing about build reproducibility. There is no open issue tracking it in the CLI repo. Reproducible PCR0 in practice comes from community approaches (Nix/deterministic-tar EIF builders, kaniko-style builds), not from AWS. So "a third party rebuilds the EIF and matches PCR0" is possible with discipline but is not a supported AWS story.

**Can AWS see enclave memory?** The docs say only that the *parent instance* cannot access enclave vCPUs/memory (https://docs.aws.amazon.com/enclaves/latest/user/nitro-enclave.html); the FAQ is silent on AWS itself and silent on memory encryption. Enclave memory is **isolated by the Nitro hypervisor, not encrypted with a key AWS lacks**; the attestation is **signed by the Nitro hypervisor with AWS's own PKI**, so the root of trust is AWS, full stop. AWS's whitepaper claims "no mechanism for any system or person to log in to EC2 Nitro hosts, access the memory of EC2 instances" (https://docs.aws.amazon.com/whitepapers/latest/security-design-of-aws-nitro-system/no-aws-operator-access.html), and the NCC Group public report (Q4 2022 engagement, published May 2023, https://www.nccgroup.com/us/research-blog/public-report-aws-nitro-system-api-security-claims/) was an **architecture review of AWS's API claims**, not an implementation audit or hardware teardown. Blunt version: Nitro Enclaves protect you from the parent instance and from AWS's *stated* operational practices; against AWS-as-adversary (or a compelled AWS) they offer a design promise and a self-signed attestation, not a silicon guarantee from an independent vendor. That is a categorically weaker trust story than SEV-SNP/TDX, and Nitro Enclaves have no GPU access, so they are not an LLM inference platform anyway. Evervault is the notable vendor still building on them.

## 4. NVIDIA GPU confidential computing

**Hardware and modes.** NVIDIA's CC Deployment Guide v7.1 (April 6 2026, https://docs.nvidia.com/cc-deployment-guide-tdx-snp.pdf) supports Hopper single-GPU CC or "Protected PCIe" 8-GPU HGX (where **NVLink traffic is unencrypted**), and Blackwell B200 single and multi-GPU with **encrypted NVLink** (whitepaper WP-12554-001 v1.3, Aug 2025, https://docs.nvidia.com/nvidia-secure-ai-with-blackwell-and-hopper-gpus-whitepaper.pdf). Blackwell CC tooling only appeared in v7.0 (Jan 2026); B300/GB300 have no CC docs I could find; Rubin/NVL72 rack-scale CC is roadmap marketing (https://www.nvidia.com/en-us/data-center/solutions/confidential-computing/). Modes: CC-Off, CC-On (encryption, bounce buffers, BMC/JTAG lockout, perf counters disabled), devtools (crypto on, counters unlocked, not for production attestation). Requires TDX (Emerald/Granite Rapids) or SEV-SNP (Milan/Genoa/Turin), kernel 6.14+, Ubuntu 25.10 for Blackwell: bleeding edge.

**What it protects.** On-die RoT and secure boot; SPDM session with DH key exchange between driver and GPU firmware; AES-256-GCM with rolling IVs on all PCIe ingress/egress via bounce buffers (TDISP/IDE inline path is "future" and needs IDE-capable switches). **HBM is not claimed to be encrypted**; it is isolated by locking down BMC/JTAG/counters. The CPU TEE contributes memory encryption and IOMMU gating of shared pages. Physical attacks beyond bus sniffing are out of scope, and TEE.fail already lists H100/H200/B100/B200 as affected.

**Attestation.** NRAS issues EAT tokens (https://docs.nvidia.com/attestation/cloud-services/latest/nras/nras_introduction.html); RIM files and OCSP come from NVIDIA services. `nvtrust` (https://github.com/NVIDIA/nvtrust, pushed Sept 2026) has **deprecated the Python SDK and Local GPU Verifier** in favor of a C++ SDK/CLI with Rust bindings, plus PPCIe verifiers. A local verifier exists but NVIDIA says standalone use is "not encouraged for production," and there is no documented bulk-downloadable RIM database; signed RIMs cached once can be re-verified offline, but discovering new golden values and OCSP need NVIDIA. I could not fetch the Device Identity CA / IK / AK cert hierarchy docs, so the chain details are unverified here.

**Composite CPU+GPU.** Azure's GA SKU is NCCadsH100v5 (SEV-SNP + H100); no Blackwell CVM SKU as of Aug 2026 docs (https://learn.microsoft.com/en-us/azure/confidential-computing/confidential-vm-overview). GCP offers a3-highgpu-1g (TDX + H100) (https://docs.cloud.google.com/confidential-computing/confidential-vm/docs/supported-configurations). Neither publishes one unified CPU+GPU token; you verify two proofs and AND them, binding the GPU report's nonce into the CPU report's REPORT_DATA yourself. Multiple 2026 arXiv papers (EnclaveX arXiv:2606.31408, PAL*M arXiv:2601.16199, arXiv:2512.05951) present exactly this stitching as a research contribution, which tells you it is not a shipped standard. Intel Trust Authority and Phala's dstack do it as a product feature.

**Overhead.** NVIDIA claims "up to 98%" of unsecured performance. Independent: ETH Zürich 4-8% at large batch (arXiv:2509.18886); 17-21% throughput / 22-28% latency on H100+TDX (arXiv:2607.19353); 45-70% when model loading dominates (ICDCS 2025, arXiv:2505.16501); naive bounce buffers 52-88% until pipelined (PipeLLM, arXiv:2411.03357). No public Blackwell encrypted-NVLink benchmarks yet. One published side channel: tokenizer memory-access patterns recover prompts on production TDX+H100 (OTRO, arXiv:2606.17358). No NVIDIA PSIRT bulletin in 2025-26 names the CC/attestation subsystem.

**Maturity.** H100 CC is production-usable on Azure/GCP; Blackwell multi-GPU CC is documented but pre-GA in every major cloud.

## 5. Vendor offerings

**Apple PCC.** GA since Oct 2024. Nodes attest to a measurement in an append-only transparency log; the device wraps request keys only to nodes whose attestation matches a logged release; researchers get the VRE and select source within 90 days (https://security.apple.com/blog/private-cloud-compute/). Verification-before-send is real but done by *your device against Apple's log*; third-party inspection is retrospective, Apple runs the log, Apple curates released source, and the VRE is a simulation. **Not available to non-Apple developers**; no API found. Best production example of the full pattern, but closed.

**WhatsApp Private Processing** (Apr 29 2025, https://engineering.fb.com/2025/04/29/security/whatsapp-private-processing-ai-tools/): CVMs with CC-mode GPUs, RA-TLS before any data, OHTTP third-party relay, a third-party log of acceptable binaries, published CVM image binaries and some source. Closest thing to your use case (E2EE messenger + server-side AI) and explicitly modeled on PCC; TEE vendor unnamed; not a third-party platform.

**Google.** *Confidential Space* is GA: vTPM-measured CVM + container digest, Google Cloud Attestation issues OIDC tokens any relying party can verify against Google's JWKS and gate via Workload Identity Pools (https://docs.cloud.google.com/docs/security/confidential-space); Google's own docs concede collaborators "assume that resource owners have reviewed and audited the container image." *Private AI Compute* (Nov 11 2025, https://blog.google/technology/ai/google-private-ai-compute/) runs Gemini on TPUs inside Titanium Intelligence Enclaves with remote attestation, an NCC Group review, and a binary-transparency story (technical brief: https://services.google.com/fh/files/misc/private_ai_compute_technical_brief.pdf) but is for Google's own products, not a developer API. No confidential Vertex/Gemini API offering found.

**Microsoft.** MAA is GA and the most mechanistically documented verifier: tokens verifiable via published OpenID metadata, MAA itself runs in SEV-SNP, measurements published, build provenance in the SCITT-based Microsoft Signing Transparency ledger (https://learn.microsoft.com/en-us/azure/attestation/overview). Secure Key Release on Key Vault/Managed HSM is GA with a JSON claim policy (https://learn.microsoft.com/en-us/azure/confidential-computing/concept-skr-attestation, https://learn.microsoft.com/en-us/azure/key-vault/keys/policy-grammar), and will accept a non-Microsoft attestation authority if its cert chains to DigiCert. NCCadsH100v5 confidential GPU VMs GA. Confidential Clean Rooms is **limited preview**, "shouldn't be used in production" (https://learn.microsoft.com/en-us/azure/confidential-computing/confidential-clean-rooms). No dedicated "Azure OpenAI runs in an attested CVM, verify here" page found.

**AWS Bedrock.** Data protection is the shared-responsibility model plus a per-region "model deployment account" that providers can't access (https://docs.aws.amazon.com/bedrock/latest/userguide/data-protection.html). Entirely trust-AWS; no attestation exposed, no evidence Nitro Enclaves are in the inference path. The 2021 "Confidential computing: an AWS perspective" post is stale and mentions no AI.

**Anthropic and OpenAI.** Nothing. Both trust centers (https://trust.anthropic.com, https://trust.openai.com) list SOC 2/ISO/etc. and no TEE or attestation product; Anthropic's newsroom through Sept 2026 has no such announcement; OpenAI's pages 403'd but no product surfaced anywhere. Privacy is contractual.

**NVIDIA.** Supplies the silicon, NRAS, and EAT tokens; no "attestable inference" product or confidential NIM found. Fortanix Confidential AI is the co-marketed enterprise wrapper with "composite attestation" but no public self-serve verifier.

**Startups (all checked live Sept 2026).**
- **Tinfoil** (https://tinfoil.sh, https://docs.tinfoil.sh): the strongest verifiable story. SEV-SNP CVM chained to NVIDIA CC-mode GPUs; measures OVMF, kernel/initrd, config hash, model weights via dm-verity; client SDKs (Go/JS/Python/Rust/Swift) verify the AMD chain **and** a Sigstore transparency-log bundle against reproducible-build measurements, then bind the attested key into TLS. Dozens of repos pushed this week. Billing layer closed and carved out of the TCB.
- **Edgeless Systems**: "Continuum" now 308-redirects to **Privatemode** (https://www.privatemode.ai/); SEV-SNP + NVIDIA CC, claims reproducible builds and transparency logs, EU-hosted, BSI C5:2026. `constellation` is archived; `contrast` (confidential containers) is the live successor.
- **Phala / dstack** (https://phala.com, https://github.com/Dstack-TEE/dstack): TDX + H100/H200/B300 GPU TEE, open framework under the CCC, powers Near AI and OpenRouter's confidential routes, per-response attestation quotes; note WireTap extracted Phala master keys on older SGX-era infra.
- **Near AI** (https://near.ai): dstack-based, Intel Trust Authority integration Aug 2026, open verifier, pay-per-token.
- **Opaque**: alive, confidential agents/RAG, no public verifier. **Anjuna**: enterprise policy manager, no self-serve. **Fortanix**: as above. **Confident Security / OpenPCC**: early access, PCC-modeled. **Evervault Enclaves**: real, Nitro-only, client verifies PCRs against AWS root in the TLS handshake; wrong hardware class for LLMs. **Super Protocol, Marlin Oyster, Secret Network (SecretVM, TDX + ITA), Duality**: real companies, thin public verification detail. **Nillion**: no concrete confidential-LLM product substantiated. **Zama** (https://www.zama.org/): pivoted to confidential blockchain finance; **FHE LLM inference is not practical in 2026 anywhere**. **Mithril Security BlindLlama/BlindAI: dead** (repos last pushed 2024-Mar 2025, blog silent since Dec 2023). Apheris, Decentriq, Protopia, Turnkey are off-topic. Cosmian's site returned 500.

## 6. The attestation-before-key-release pattern

**Standards.** RFC 9334 defines Attester/Verifier/Relying Party/Endorser/RVP and passport vs background-check models (https://datatracker.ietf.org/doc/rfc9334/). **EAT is RFC 9711 (April 2025)**. The RATS WG page (https://datatracker.ietf.org/wg/rats/documents/) lists the Conceptual Message Wrapper and EAT Measured Component as published RFCs in July 2026 (numbers reported as RFC 9999 and 10013; I did not independently confirm those numbers). **CoRIM/CoMID, the reference-value format, is still a draft** (rev -11, WGLC, https://datatracker.ietf.org/doc/draft-ietf-rats-corim/), as is AR4SI (rev -10). DAA and evidence-transformation drafts expired. Consequence: every production key-release system uses proprietary claim/policy formats; there is no interoperable "expected measurements" standard yet. Veraison (https://github.com/veraison) is the actively maintained open-source Verifier that implements EAR/CoRIM ahead of the specs, used inside Trustee, but not a hosted product with documented production users.

**CCC project health** (GitHub pushes checked): Gramine, Open Enclave, Keystone, Trustee/KBS, Keylime, virtee, Veraison, COCONUT-SVSM, dstack, spdm-rs all active; Islet slower; **Enarx and Occlum effectively dead**; ManaTEE stalled; Constellation archived. Arm CCA appears in no hyperscaler SKU (Azure's June 2026 catalog lists only SEV-SNP and TDX, https://learn.microsoft.com/en-us/azure/confidential-computing/overview-azure-products); RISC-V CoVE is unratified. Neither matters for 2026-27 designs.

**Key release in production.** Azure SKR (GA), AWS KMS attestation conditions (GA, now also NitroTPM), GCP Confidential Space + Workload Identity (GA) all work and all share the same shape: **the policy is owned and mutable by the cloud account owner, with no external change log.** Cloud-independent: Confidential Containers Trustee/KBS (AS + KBS + RVPS, maps 1:1 to RFC 9334, https://github.com/confidential-containers/trustee, active, self-hosted, still churning); Keylime for continuous TPM monitoring; no GA Vault plugin found. One cautionary 2026 CVE in a confidential-AI aTLS relay (Cocos, CVE-2026-33697) shows the software glue above attestation is where bugs land.

**What an outside relying party can concretely check today:** (1) the signature chain to AMD/Intel (or AWS/Google/Microsoft) on a report containing (2) a measurement they pin from an out-of-band trusted source, (3) a fresh nonce/ephemeral key in REPORT_DATA, (4) TCB/SVNs above a minimum they maintain, (5) policy bits (debug off, SMT/migration as desired, ciphertext hiding on), and (6) for GPUs, an NRAS/nvtrust verdict nonce-bound to the CPU report. Then encrypt the group key to the attested ephemeral key (HPKE/RA-TLS). That is enough to make "the key goes only to this measured code" true at the moment of release.

**What breaks and what you must add yourself:**
- *Measurement → source*: needs reproducible builds and a public log of every measurement you will ever accept (Sigstore/Rekor is the general tool; Apple, WhatsApp, Tinfoil and Privatemode are the ones that actually do it). Without this, a measurement is an opaque hash the operator hands you.
- *Redeploy-tomorrow*: only closed if clients refuse any measurement not in the log and the log is append-only and externally monitored. No hyperscaler ships this.
- *Runtime state*: launch measurements cover initial memory only; use dm-verity into the measured cmdline so the whole image is in the hardware hash, and treat vTPM/IMA chains as weaker.
- *TOCTOU and key lifetime*: attestation gates the handoff, not what the code does afterwards; re-attest per session, keep keys ephemeral, and design so a key-holding enclave can be rotated out.
- *Physical adversary*: 2025-26 interposer work forged attestation on every major TEE and on NVIDIA GPUs, and vendors declined to fix it. Your real guarantee is against the cloud's *software* stack and honest-but-curious operators, not against a data-center insider with a $50 board.
- *Nitro specifically*: the root of trust is AWS's own PKI and hypervisor; there is no independent silicon vendor to appeal to.

**Recommended posture for the group-chat-key case:** SEV-SNP or TDX CVM (not Nitro) with H100 CC if inference is in the TCB; dm-verity image with reproducible build, measurement published to a transparency log clients enforce; client-side verification via `snpguest`/DCAP + nvtrust with pinned roots and an actively maintained minimum-TCB policy; per-session RA-TLS/HPKE key wrapping; and an explicit statement to users that the threat model excludes physically-present adversaries and the silicon vendor.
